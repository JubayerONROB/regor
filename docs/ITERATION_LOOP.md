# Iteration loop

```
run approved experiments → collect → validate → analyze → report → compare
      ↑                                                            ↓
 execute approved  ←  researcher decision  ←  ranked proposals  ←  unresolved questions
```

## Proposals (`research propose`)

Generated by transparent rules over files. Each proposal records: what was learned,
the remaining uncertainty, the hypothesis to test, why it is necessary, the variables
that change, what stays controlled, the possible outcomes, how the outcomes would
influence the research, and the resources and estimated hours.

| Rule (`kind`) | Trigger |
|---|---|
| `diagnose_failure` | an experiment has failed runs and no validated run |
| `replicate` | validated runs < `statistics.min_replicates` (suggests the next seeds) |
| `review_provisional` | provisional runs exist |
| `baseline` | a `proposed` experiment has no baseline in `compare_with` |
| `ablation` | a validated `proposed` experiment has no ablation |
| `variance_investigation` | coefficient of variation > 0.2 over ≥ 3 runs |
| `increase_sample` | a comparison is untested or not significant after adjustment (with an indicative normal-approximation power estimate) |
| `resolve_contradiction` | claims contradict each other |
| `design_experiment` | a hypothesis has no experiment |
| `evidence_gap` | a research question has no experiment |

Ranking: `score = 0.4 × relevance + 0.4 × information_gain + 0.2 × feasibility`
(documented in `iteration.py`). It orders the list. It does not decide anything.

Duplicates are suppressed: a proposal with the same signature and unchanged evidence is
not proposed again, which avoids re-running similar experiments without a reason.

## Decisions **[researcher]**

`research proposals approve|reject PID --by NAME [--note ...]` records the decision in
`docs/decisions/decision_log.yaml`. Approving a proposal does **not** run anything: the
experiment still goes through preflight, and through a run approval if one is required.

## Iterations and stopping

`research loop start --by NAME` groups the approved proposals into an iteration, and
`research loop close --summary ...` records how many new verified claims it produced.

`research loop status` evaluates:

| Criterion | project.yaml | Effect |
|---|---|---|
| max iterations | `stopping.max_iterations` | must stop |
| compute budget | `stopping.compute_budget_hours` (sum of run runtimes) | must stop; also blocks new runs at preflight |
| deadline | `stopping.deadline` (ISO date) | must stop |
| saturation | `stopping.saturation_window`: N closed iterations with zero new verified claims | must stop |
| review checkpoint | `stopping.require_review_every` closed iterations without `research loop review` | review required |
| minimum evidence | every hypothesis has a verdict and every RQ a verified claim | reported (suggests stopping) |

Progress is not only "better numbers": refuted hypotheses, robustness failures and
efficiency trade-offs are verified claims like any other.

Major changes to research questions, datasets, methodology or evaluation protocols
require the researcher's approval and a `research decision add` record.
